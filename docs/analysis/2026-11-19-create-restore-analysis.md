# 方案分析报告：create / resume 的 55–70 ms 到底花在哪，kuasar 的内存恢复该怎么走

> 日期：2026-11-19 · 环境：cube90 / 2C2G / `python:3.12-slim` 模板
> 目的：把"创建和恢复为什么慢"从现象拆到根因，并给出三条可选路线。
> 读法：第 0 节是结论，赶时间只看它；第 1 节是名词解释（不讲内核细节）；第 2–6 节是证据与账本；第 7–9 节是用户视角与方案。

---

## 0. 一页结论

1. **慢的不是 vsock、不是 MUX、不是恢复时的"握手闸门"（gate）。** 我们先后把 gate 去掉、把 MUX 的重建挪走，create/resume 几乎没变。
2. **真正的原因是"内存恢复方式"：** restore 后 guest 第一次被唤醒时，会连续触碰约 **1 万页**内存；我们的方案里，**每一页都要由用户态进程从快照拷一份进 guest 内存**，每页约 5 微秒，1 万页就是 **50 毫秒**。
3. **证据很直接：**
   - restore 完成后，第 2 次、第 3 次连接只要 **约 1 毫秒**；
   - 但第 1 次连接要 **55–70 毫秒**；
   - 在这 55–70 毫秒里，计数器显示拷了 **4,700–9,965 页（约 20–40 MB）**。
4. **CubeSandbox 没有这个成本**，因为它的 guest 内存是**直接映射本地文件**的，缺页由内核处理，不做"每页一次用户态拷贝"。
5. **我们为"跨节点、去重、压缩、加密"付出的成本，大部分落在 create/resume 这条高频路径上；而这些能力对应的场景是低频的**（节点维护、故障恢复、扩容分发）。用一个高频操作去补贴低频能力，账算不过来。
6. **建议：**
   - **方案 A（先做，1–2 周）：** 在启动前把模板内存顺序预填进 guest，把"1 万次随机缺页"变成"一次顺序拷贝"，预计第 1 次连接 55–70 → **5–15 ms**；
   - **方案 B（更彻底）：** 模板在本地物化成整块内存镜像，restore 直接映射，缺页由内核处理（Cube 的做法），第 1 次连接可到 **1–3 ms**；
   - **方案 C（产品选择）：** 如果产品不承诺"跨节点续命/去重/加密"，**直接采用 CubeSandbox 的模型**，不要继续在这条路上投入。

## 1. 先把名词说清楚

这一节给不熟悉内核的同学。已经懂 UFFD 的可以跳到第 2 节。

**缺页（page fault）**
程序访问一块"还没真正装进内存"的地址时，CPU 会暂停这条指令，交给操作系统去把数据准备好。准备好之后程序继续跑，像什么都没发生。

**UFFD（userfaultfd，用户态缺页处理）**
一种让"缺页"由**用户态程序**处理的机制。guest 碰到缺页时，内核不自己处理，而是通知我们的程序；我们的程序去快照里找到这一页，拷进 guest 内存，guest 才继续。
好处：不用一次性把 2 GB 内存全加载，用到哪页取哪页。
坏处：**每页都要走一次"内核通知 → 用户态处理 → 拷 4 KB → 唤醒"的往返，约 5 微秒。**

**minor fault（次要缺页）**
如果数据本来就在操作系统的文件缓存里，内核只需要"把这一页映射进地址空间"，**不需要拷贝**，成本约 0.5–1 微秒。
CubeSandbox 走的就是这条路。

**chunk（内容分块）**
把大文件切成小块（我们默认 128 KiB–1 MiB，平均 512 KiB），每块按内容算一个"指纹"（哈希）。内容相同的块只存一份。
一个 512 KiB 的块大约等于 **128 页**（每页 4 KiB）。

**manifest（内容清单）**
一份"这个快照由哪些块组成"的清单。因为块是按内容命名的，所以不同模板/不同沙箱可以共享相同的块，这就是"去重"。

**reflink（文件系统写时复制）**
文件系统层面的"克隆"：两个文件共享同一批磁盘块，谁写谁才复制。成本接近 0，但只在**同一台机器、同一种文件系统**上成立，也不能跨模板按内容去重。
CubeSandbox 用的是这个。

**gate（恢复闸门）**
我们之前的 restore 流程里，guest 必须先处理一个"传输层重置"事件，host 才能和它通信。这段时间就是闸门。**它不是根因，只是"等待窗口"和缺页风暴恰好重合。**

## 2. 我们测到了什么

### 2.1 测量方法（一句话版）

- 给 conductor / runner / 沙箱运行时打了计时标记，每个操作从开始到结束的每一段都有毫秒级记录；
- 用 `journalctl` 把日志和标记对齐，拼成"阶段树"；
- 客户端脚本记录每次 create / pause / resume 的墙钟时间；
- 另加两个"探针"：restore 完成后立刻再连两次 guest、再连一个没人监听的端口，用来判断"是路径慢，还是第一次慢"；
- 加了一个"人为延迟拨号"的开关（0/10/20/…/80 ms），用来判断"是不是在等 guest 就绪"。

### 2.2 基础数据（C=1，9 次，已开 runner 池）

| 操作 | 耗时 |
|---|---:|
| create（客户端，含 26 ms 状态轮询） | **244.7 ms** |
| pause | **192.9 ms** |
| resume | **260.8 ms** |

restore 内部（resume 的一次）：

| 阶段 | 耗时 |
|---|---:|
| 打开元数据 + 准备内存源 + 重建磁盘 | 17 ms |
| 启动 Cloud Hypervisor + 等 API 就绪 | 35 ms |
| `/vm.resume`（虚拟机真正恢复） | **1.6 ms** |
| **和 guest 建立控制连接（dial）** | **55–70 ms** |
| guest 侧恢复处理（时钟/网络/MUX/解冻） | 38–40 ms |

### 2.3 关键实验：到底在等什么

**实验一：restore 完成后立刻再连两次 guest**

| 探针 | 结果（14 次 restore） |
|---|---|
| 第 2 次连接 | **1.12 ms** |
| 第 3 次连接 | **1.26 ms** |
| 连一个没人监听的端口 | **0.37 ms**（立刻被关闭） |

→ 路径本身没问题，**只有第一次连接慢**。

**实验二：把这 55 ms 拆开**

- 连上 Cloud Hypervisor 的本地 socket：**0.03 ms**（一点都不慢）；
- 等 guest 接受连接并回 `OK`：**55–70 ms**（全部在这里）。

**实验三：人为延迟拨号（0/10/20/30/50/80 ms）**

| 延迟 | 0 | 10 | 20 | 30 | 50 | 80 ms |
|---|---:|---:|---:|---:|---:|---:|
| 第一次连接耗时 | 55.3 | 61.6 | 48.4 | 66.3 | 72.9 | 42.6 ms |

→ **没有"越晚越快"的曲线**。说明不是"等 guest 就绪"，而是**第一次连接本身触发了 guest 侧的大量工作**。

**实验四：这 55 ms 里 guest 在干什么**

在同一窗口统计内存缺页处理器（UFFD）的计数：

| 指标 | 每次 restore |
|---|---:|
| 被拷进 guest 的页数 | **4,700 – 9,965 页** |
| 其中来自快照加载的页 | 133 – 533 页 |
| 唤醒次数 | 13 – 49 次 |

**4,700–9,965 页 × 约 5 微秒/页 ≈ 25–50 毫秒**，和第一次连接的 55–70 ms 完全对得上。

### 2.4 顺手被证伪的两个猜想

- **"是恢复闸门（gate）在挡"**：把闸门去掉（把重置提前到暂停阶段）后，第一次连接只快了约 12 ms（67.1 → 54.7 ms），客户端只快 6 ms（260.8 → 255.0 ms）。闸门不是根因。
- **"是 MUX 重建慢"**：MUX 重建只占 10–17 ms，且在 guest 侧恢复处理的 40 ms 里；去掉它也不会消掉 55 ms 的连接成本。

## 3. 为什么第一次连接会触发这么多缺页

restore 时我们只恢复了"虚拟机的状态"，内存里的页大部分还留在快照里。第一次连接会同时触发：

1. guest 的网络协议栈、socket 缓冲区、中断/队列相关的内核代码和数据页；
2. guest 里的 agent/应用被唤醒后，它自己的工作集（代码、堆、栈）；
3. 连接建立过程中分配的各种临时缓冲区。

这些页都是**第一次访问**，所以每一页都触发一次 UFFD 事件，每一页都要从快照拷进 guest。等这波过去，页都在内存里了，所以第 2、3 次连接只要 1 ms。

**这就是为什么"删闸门"没用**：闸门只是让我们"等"这波缺页做完；不等，第一次连接就自己去做这波缺页。时间不会消失，只是换了个地方记账。

## 4. kuasar 和 CubeSandbox 的机制对比

| | kuasar（现在） | CubeSandbox |
|---|---|---|
| guest 内存从哪来 | 新建一块空内存，缺页时按页从快照**拷**进去 | 直接映射本地内存卷文件 |
| 缺页由谁处理 | 用户态进程（每页一次往返 + 4 KB 拷贝） | 内核（页已在文件缓存里，只建立映射） |
| 每页成本 | **约 5 微秒** | **约 0.5–1 微秒，且不拷贝** |
| 1 万页成本 | **约 50 毫秒** | **约 5–10 毫秒** |
| 产物形态 | 内容分块 + 清单（可去重、压缩、加密、远端取块） | 本地内存卷（文件系统克隆） |
| 跨节点 | 可以把块放到对象存储，按需拉取 | 内存卷要在本节点（共享存储或整卷搬） |
| 存储 | 块级去重 + 压缩 + 加密 | 文件系统 reflink（同模板共享块），无压缩/加密 |

一句大白话：

- **我们的做法**：guest 缺一页，就按门铃叫管理员去仓库取一本来，取来还要复印一份；
- **Cube 的做法**：书本来就在书架上，管理员直接把书递过去，不用复印。

## 5. 成本账：压缩、加密、分块、去重

### 5.1 压缩和加密：用 CPU 换空间，热路径上是税

- 我们的块是 **AES 加密 + Snappy 压缩**。Snappy 解压约 2–5 GB/s，AES 约 1–2 GB/s。
- 40 MB 的数据，解密 + 解压大约 **15–40 ms**。
- 有自适应规则：只有"至少省 4 KiB 且压到 ≤75%"才压缩，压不动的页原样存；全零页根本不进块。所以最坏情况不会发生，但**这笔 CPU 开销是实打实的**。
- 结论：压缩/加密适合"存储贵、要跨网络、要静态加密"的场景；在单机本地、追求延迟的 create 路径上，它是**纯成本**。

### 5.2 按块走网络：不是延迟优化

- 一个块平均 512 KiB，40 MB 工作集约 80 个块。
- 1 Gbps 网络：一个块约 4 ms；串行 80 个块 = 300+ ms；16 路并行 ≈ 30–60 ms。
- 本地缓存 + UFFD 约 50 ms。
- 所以"边跑边从远端拉块"在延迟上赢不了本地；它赢的是"**不用把整个 2 GB 快照搬到节点**"。
- 正确用法：**每节点拉一次、放进本地缓存**（像拉容器镜像），热路径只用本地缓存。跨节点恢复是"冷路径"。

### 5.3 去重：省存储，但维护复杂

- 我们的去重粒度是"内容块"（128 KiB–1 MiB），跨模板、跨沙箱都能共享；代价是引用计数、垃圾回收、缓存淘汰、并发合并请求、加密校验——都是真实的工程复杂度。
- Cube 的去重是文件系统 reflink（块级、同机、同模板），维护成本低，但跨模板不生效。
- 结论：去重适合"大量同源沙箱 + 存储成本敏感"；对单机少量沙箱，收益有限。

## 6. 跨节点在 agent 场景到底多常用

| 场景 | 什么时候发生 | 频率 | 是热点吗 |
|---|---|---|---|
| 模板分发到新节点 | 扩容、新节点加入 | 每次扩容一次，之后本地缓存 | 半热（首次拉取） |
| 节点维护/重启 | 升级、硬件维护 | 每周/每月 | 冷 |
| 节点故障 | 宕机、磁盘坏 | 偶发 | 冷（影响大） |
| 暂停沙箱跨节点续命 | 长会话 + 节点下线 | 少 | 冷 |
| 跨区域/跨 AZ 恢复 | 合规、就近、区域故障 | 很少 | 冷 |
| 负载再平衡 | 热节点搬冷节点 | 视是否做自动均衡 | 冷 |
| 快照导出/分享 | 复现、共享模板 | 很少 | 冷 |

真正的热点是：

- **每次请求都要做的本地 create**；
- **同一个节点上 pause 几分钟再 resume**（agent 空闲后唤醒，非常常见）。

跨节点是"保险"，不是"日常通勤"。**把一个高频操作的成本，花在低频的保险能力上，就是我们现在这笔账的问题。**

## 7. 从用户角度，最后能感知到什么

剥掉所有内部实现，用户只感知四件事：

| 用户能感知 | kuasar 现在 | CubeSandbox | 说明 |
|---|---|---|---|
| **快不快** | create ~245 ms、resume ~261 ms（含轮询） | create ~57 ms、resume ~93 ms | 第一印象 |
| **API 顺不顺** | 创建后是 `starting`，要轮询；SDK 直接下命令可能失败 | 返回即可用 | 兼容性/报错率 |
| **沙箱丢不丢、能不能搬** | 快照可发布到对象存储，可在别的节点恢复 | 本地内存卷，跨节点需共享存储或搬卷 | 容灾/迁移 |
| **能不能装进我的环境** | 不要 containerd，systemd 即可 | 需要 containerd + CNI | 交付形态 |

其余的内部实现（UFFD、分块、加密、MUX、vsock 闸门）**用户完全感知不到**。

## 8. 三条路线

### 方案 A：顺序预填充（推荐先做，1–2 周）

**做法：** 在 `/vm.resume` 之前，把模板内存里"常驻的页"按顺序写进 guest 内存。这样 guest 第一次访问时页已经在内存里，不触发 UFFD 事件。

**预期：** 第一次连接 55–70 → **5–15 ms**；create/resume 各降约 **40–50 ms**。

**代价：**
- 一次顺序拷贝（几十 MB，约 10 ms），比 1 万次随机缺页便宜；
- 预填充了但没被用到的页，是少量浪费；
- 不动物产模型、不动 guest ABI、不需要模板重建。

**风险：** 如果常驻内存很大（比如几百 MB），顺序拷贝本身也会变慢；需要先测"常驻页数"，并只填启动阶段真正会用到的部分。

### 方案 B：本地镜像直接映射（更彻底，2–4 周）

**做法：** 模板在节点上先"物化"成一整块内存镜像文件；restore 时直接映射成 guest 内存，缺页由内核处理（minor fault），不再经过用户态拷贝。

**预期：** 第一次连接 **1–3 ms**；但首次物化需要时间/空间。

**代价：** 改内存载体；需要物化/缓存/垃圾回收；跨节点仍可保留 manifest 作为"分发层"，但热路径用本地镜像。

### 方案 C：换 CubeSandbox 的模型（产品选择）

**适用条件：** 产品不承诺跨节点续命/去重/加密，且部署环境有 containerd。

**收益：** 直接拿到 ~57 ms 的 create 和文件映射的恢复路径；**代价**是放弃可移植产物、无 containerd 部署和通用运行时。

### 对比

| | 改动量 | create 预期 | 保留产物模型 | 适合 |
|---|---|---|---|---|
| A 预填充 | 小 | ~190–200 ms | 是 | 先止血 |
| B 直接映射 | 中 | ~150–170 ms | 是（冷路径） | 想要接近 Cube |
| C 换 Cube | 大 | ~57 ms | 否 | 产品不需要那三样 |

## 9. 建议与下一步

1. **先做 A**：成本最低、可回退，能拿回一半以上的损失；做完再测是否值得做 B。
2. **把"热路径"和"冷路径"分开**：
   - 热路径：本地模板/本地缓存 → 预填充或直接映射；
   - 冷路径：manifest/对象存储 → 只用于首次分发、容灾、迁移。
3. **如果产品定位不包含跨节点/去重/加密**：别修了，直接用 CubeSandbox，省下的是整个平台的维护成本。
4. **验证方式**（避免再被"看起来变快"骗）：
   - 同一二进制、同一模板、交替 A/B；
   - 看 `第一次连接耗时`、`总 restore`、`create/resume 客户端`三项；
   - 负向对照：关掉预填充，第一次连接必须回到 55–70 ms，否则测量无效；
   - 功能回归：日志完整、exec 并发、envd 初始化、pause/resume 100 次。

## 10. 附录：测量口径与局限

- 环境：cube90，容器内运行，cgroup v1，2C2G 模板（`python:3.12-slim`），已开 runner 池；
- 每个数字来自 9–14 次重复；客户端数字含 50 ms 间隔的状态轮询，因此有约 26 ms 的量化误差；
- 对照组 CubeSandbox 的数字来自其公开基准（v0.7.1，C1），**镜像与工作负载不同**，只能看量级；
- 我们测到的 50 ms 还没有拆成"UFFD 往返 / AES / Snappy / 拷贝"四份；可以用"关闭加密压缩的实验快照"再拆一次；
- 本次涉及的实验代码（闸门、探针、标记）默认关闭，不影响生产路径。

---

**一句话总结：** 慢的根因是"每页一次用户态拷贝"的内存恢复方式，不是网络协议；删闸门、删 MUX 都没用。先做"顺序预填充"止血，再决定要不要走"本地镜像直接映射"；如果产品根本不需要跨节点/去重/加密，直接用 CubeSandbox 才是省力的选择。
